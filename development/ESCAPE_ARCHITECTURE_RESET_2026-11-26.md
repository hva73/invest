## 3. Beslutningsforslag: modulær monolit
Behold Python, JavaScript, SQLite og eksisterende hosting. Ingen ny tjeneste, framework, registry eller parallel motor uden dokumenteret behov. Adskil ansvar i eksisterende moduler før eventuel fysisk flytning:
- Kilder: hotwatch_adapters, eodhd_feeds, market_data, portfolio_data, mcp_client. Normaliser én gang ved grænse; bevar provenance og kilde-/modtagelsestid. Identitet: instrument_resolver og verificerede feed links, samlet valideringsvej; ingen ticker-only match.
- Fælles markedsevidens: genbrug observationer og beregninger ved identisk nøgle; bounded cache/retention, provider-budget og rettigheder. Brug eksisterende feed reuse og capacity, ingen ny dublet.
- Domæne: hotwatch_features (pure), hotwatch_strategy (versioned), trading_engine_v2 (simulations-only, lovende types). Strategi og risiko evalueres deterministisk på validerede inputs; adskilte entry, position exit, long-term policies. En autoritativ beslutningsprojektion med freshness revocation ved læsning; ingen nye strategibeslutninger i UI.
- Orkestrering: hotwatch_service og engine samler mange ansvar. Udtræk små rene funktioner, hold scheduling, storage, beregning, events adskilt. Leases, deadlines og kill switches bibeholdes. Ingen netværk under DB-skrivelås. Bevar transaktionel atomaritet, revalidér input ved commit.
- Handel: trade_service håndterer proposal/estimate/status, fælles immutable identity validator. Valider kildens intent/asset/portfolio/collection/side og korreleret order-ID. Gem original receipt særskilt fra refresh, afvis modstridende eller uverificerede bindinger; tillad legitime historiske recovery. Fill kun fra brokerbevis. Realiseret P&L fra faktisk solgte andele med korrekt cost basis/FX/gebyrer og separat køb/salg-provenance.
- Persistence: behold SQLite og eksisterende skema indtil målt behov; isolér queries, engangsmigrationer og runtime startup. Additive migration, reversible deploy, ingen historiesletning. Dashboard projection leverer konsistent visningsdata med kilde og missing reason.
- UI: eksisterende responsive design, én fælles session/interaction lifecycle med monotont intent-token og guarded DOM/state writes og errors efter await. AbortController hvor relevant, men correctness må ikke afhænge af abort. Ingen private uploads/POST efter sessionskift; server-side CSRF/ownership stadig obligatorisk. Separate render og events, normal kildeformatering. Bevar archive pagination/polling og normal refresh.
- Release: eksisterende Nordicway-godkendelse, exact SHA, manifest, plads/kvote, backup, quiesce, integrity, health og retention. Ingen ny releaseplatform.
