# Nordicway: begrænset diagnostik og releaseforberedelse

Status: **udvikling og offline-tests** under Issue #16. Intet workflow er aktiveret, ingen SSH-forbindelse eller installation er udført, og dette er ikke en færdig deploymentfunktion.

Den forberedte GitHub Actions-del accepterer kun repository-ejerens faktiske GitHub-identitet, udviklingsgrenen og enten manuel kørsel eller en ny, strengt valideret kommentar på Issue #16. ChatGPT og Codex deler GitHub-identiteten; workflowet kan ikke kryptografisk skelne mellem dem. Et replay kan gentage et læseopslag, men kan ikke udløse installation eller en vilkårlig kommando.

Den dedikerede læsenøgle skal på serveren tvinges til en forudinstalleret, gennemgået guard med `authorized_keys` forced command samt forbud mod viderestilling og pty. Guarden accepterer kun de to faste operationer diagnostik og read-only releaseforhåndskontrol; runneren sender ingen kode. Serverens eksisterende nøgler må ikke genbruges som ubegrænset diagnostiknøgle. Installation af guard, ejerskab, rettigheder, isolation og negative forsøg skal gennemgås og godkendes særskilt; ingen installation er udført. En miljøvariabel er en administrativ bekræftelse, ikke selvstændigt bevis for begrænsningen. En fremtidig deployment skal bruge særskilt privilegeret identitet og yderligere godkendelse.

Output filtreres på runneren til et begrænset schema: installeret versionsmarkør, aggregeret heartbeat-/session-/køstatus, procesantal og filsystemets ledige plads. Versionsmarkøren beviser ikke, at kørende processer bruger præcis denne kode. Filssystemets ledige plads er ikke det samme som kontoens ledige kvote. Ukendte eller usikre forhold oplyses som ukendte; rå fejltekster, procesargumenter, credentials og depotoplysninger medtages ikke. Fjernsvaret har størrelses- og tidsgrænser.

Før et senere faktisk SSH-forsøg kræves **uafhængig** bekræftelse af Nordicways hostnøgle, ikke blot nøgle set ved et tidligere forbindelsesforsøg. Administrator skal derefter konfigurere GitHub Environment `ESCAPE_NORDICWAY_READONLY` og dets variable `ESCAPE_NORDICWAY_READONLY_AUTHORIZED=1` og `ESCAPE_NORDICWAY_RESTRICTED_KEY_VERIFIED=1` samt de dedikerede secrets `ESCAPE_NORDICWAY_KNOWN_HOST`, `ESCAPE_NORDICWAY_VERIFIED_FINGERPRINT`, `ESCAPE_NORDICWAY_SSH_PRIVATE_KEY` og eventuelt `ESCAPE_NORDICWAY_SSH_PASSPHRASE`. Den sidste variabel må først sættes efter faktisk kontrol af serverens forced command og afvisning af andre kommandoer. Secretindhold må aldrig skrives i repository eller chat. Den offentlige hostnøgle skal matche den uafhængigt bekræftede fingerprint. Den private nøgle indlæses via pipe i en kortlivet `ssh-agent`; den skrives ikke i en nøglefil af workflowet. Indtil disse forudsætninger er opfyldt, stopper workflowet før SSH.

Efter særskilt review/aktivering er den faste anmodning på Issue #16 `ESCAPE_SERVER_READONLY_V1 {"request_id":"<32 små hextegn>"}`. Forhåndskontrol bruger de samme data og tilføjer kun `"operation":"release_preflight"` samt `"sha":"<40 små hextegn>"`. Ingen frie kommandoer accepteres. Resultat findes i Actions-loggen; ukendt eller mislykket output må ikke tolkes som PASS.

Releaseforhåndskontrollen accepterer kun en præcis commit, ren checkout og de faktiske, sporede manifestfiler. Den sammenligner filindhold med Git-objekter og afviser symlinks og uventede stier. Den foretager ingen backup, installation, migration eller genstart. Den returnerer altid `blocked`, fordi ejergodkendelse, kontokvote, verificeret stop/genstart af Passenger samt afprøvet restore stadig mangler. En commit-hash er ikke i sig selv en godkendelse. Den eksisterende `apply_update.py` dækker alene dele af backup og kodekopiering og er ikke bevis for fuld migrations- eller produktionsrollback.

Før #16 kan færdiggøres, skal den samlede ejer-godkendte deployment, konsistent backup og reelt afprøvet restore/stop/start/health/readback implementeres og testes. Særlig ejerbeslutning er stadig nødvendig for faktisk installation; ingen handler eller ændringer af handelsmandat er en del af dette arbejde.
